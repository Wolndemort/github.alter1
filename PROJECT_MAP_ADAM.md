# Карта проекта ALTER

## Поток сообщения

```text
Telegram
  ├─ текст ────────> handler ─> сессия PostgreSQL ─> OpenRouter ─> ответ
  ├─ голосовое ────> Whisper ─> текстовый контекст ─> OpenRouter ─> ответ
  ├─ фото ──────────> base64 image + session context + memory ─> vision-модель ─> ответ в том же диалоге
  ├─ видео ─────────> ffmpeg ─> кадры + аудио + session context ─> vision + Whisper ─> ответ
  ├─ музыка ────────> YouTube API ─> ссылки
  ├─ «включи песню» ─> YouTube API ─> yt-dlp/ffmpeg ─> MP3 ─> Telegram Play
  ├─ актуальный вопрос > Tavily ─> выдержки и ссылки ─> AI fallback ─> ответ + источники
  └─ погода ────────> wttr.in ─> текущая погода
```

## Слои

`main.py` запускает aiogram, Redis, PostgreSQL-сессии и фоновые задачи.

`handlers/user_handlers.py` принимает текст, команды, голосовые, фото и видео.

`utils/ap_logic.py` формирует ответы, вызывает модели OpenRouter и обрабатывает долговременную память.

Маршрут модели анализирует только пользовательские сообщения: простой запрос идёт на быструю модель, а планирование, сравнение, код и длинные задачи — на reasoning-модель. Системный prompt и объём сохранённой памяти не делают обычный запрос искусственно «сложным».

`utils/ap_logic.py` также содержит ограниченный tool loop с allow-list для web search, погоды и YouTube. Ошибка отдельного инструмента передаётся обратно модели как недоступный инструмент и не роняет диалог.

Этот loop работает как planner/executor: модель сначала выбирает нужный инструмент по смыслу и формирует аргументы, ALTER выполняет только разрешённую операцию, валидирует результат (`ok`/`empty`/`error`), возвращает его модели и делает до шести итераций (лимит настраивается `TOOL_MAX_ROUNDS`, жёсткий максимум — 12), если нужен следующий шаг. Обычные web/weather/media-запросы и audio action не зависят от фиксированных trigger-фраз.

`utils/web_search.py` выполняет веб-поиск через Tavily. Результаты поиска передаются в `generate_reply` вместе с заголовками, выдержками и URL. Веб-поиск не заменяет AI-модели: он поставляет актуальный контекст, а ответ формирует первая доступная модель из цепочки Gemini → GPT → Claude.

`utils/youtube_search.py` отдельно работает с YouTube Data API и используется для поиска музыки и видео.

`utils/audio_search.py` скачивает первый найденный YouTube-результат как MP3 192 kbps. `handlers/user_handlers.py` отправляет его через `answer_audio`, после чего удаляет временный файл. Если пользователь просит «найди», «пришли ссылку» или «покажи видео», работает обычный режим YouTube со ссылками и превью; если просит «включи», «пришли песню» или «скачай песню», работает аудиорежим без дублирования ссылок.

В `generate_reply` задан характер ALTER: использовать память по теме, не выдумывать факты, не повторять память дословно и иногда задавать один уместный вопрос. Категория `open_loops` предназначена для незавершённых дел и тем, к которым можно вернуться позже.

`utils/tasks.py` закрывает неактивные сессии, обновляет память, отправляет напоминания и check-in. Для явных упоминаний боли или плохого самочувствия создаётся отдельный мягкий `health_checkin`; его задержка и частота обычных check-in настраиваются в `User.tech_stack`. Тихие часы не дают фоновым сообщениям прийти ночью.

После таймаута `monitor_personality_imprint` передаёт историю в модель, объединяет найденные факты с памятью пользователя и отдельно сохраняет важные события. `monitor_checkins` раз в несколько минут отправляет мягкое сообщение только пользователям с включёнными check-in и не чаще одного раза в сутки.

Модели задаются в `.env`: `google/gemini-2.5-flash` → `openai/gpt-4o-mini` → `anthropic/claude-3.5-haiku`. Список используется последовательно, поэтому временный сбой основной модели не останавливает ALTER. Для веб-поиска нужен `TAVILY_API_KEY`; ключ не хранится в Git.

`middleware/` передаёт DB-сессию и ограничивает частоту запросов.

`utils/metrics.py` собирает in-process-счётчики и тайминги. Каждое событие дублируется в обычный grep-friendly лог (`metric_count=...`); смотреть их можно через `docker compose logs -f bot | grep metric`. Метрики сбрасываются при рестарте, поэтому это текущий диагностический слой, а не долговременное хранилище.

`utils/runtime.py` выполняет preflight Redis/PostgreSQL до polling и завершает локальный запуск понятным сообщением, если зависимости недоступны. Это позволяет проверять код без запуска Docker.

`tests/test_smart_eval.py` — сценарный eval-слой: проверяет, что память отбрасывает неизвестные категории, исправления заменяют старые scalar-факты, `open_loops` сохраняются, обычная беседа не запускает поиск, сложные задачи выбирают reasoning-модель, а инструменты ограничены allow-list.

`utils/quality.py` выполняет дешёвую проверку финального текста после AI: пустой ответ, размер, число вопросов, утечка tool/system деталей и наличие атрибуции источников. Это наблюдаемость и защита качества, а не попытка заменить глубокий eval фактологии.

`data/models.py` содержит таблицы `users`, `session`, `important_events`, `reminders`.

`alembic/versions/` хранит последовательные изменения схемы базы.

`docker-compose.yml` поднимает bot, PostgreSQL, Redis и отдельный контейнер миграций.

`scripts/backup-db.sh` создаёт custom-дамп PostgreSQL вместе с векторными embedding-данными, проверяет его через `pg_restore --list`, защищает запуск от параллельных копий и удаляет локальные архивы старше 14 дней.

`scripts/backup-db-to-s3.sh` сначала запускает локальный backup, затем загружает проверенный `.dump` в Yandex Object Storage через S3 API и проверяет его через `head-object`. Облачные копии хранятся минимум 90 дней (`CLOUD_RETENTION_DAYS=90` по умолчанию), после чего старые объекты удаляются. Секреты лежат только в `/root/alter/.backup.env`, который исключён из Git.

На VPS используется одна cron-запись:

```cron
0 4 * * * cd /root/alter && /bin/bash ./scripts/backup-db-to-s3.sh >> /var/log/alter-backup.log 2>&1
```

Ручная проверка: `./scripts/backup-db-to-s3.sh`. Локальные файлы находятся в `/root/alter/backups/`, облачные — в `s3://<bucket>/postgres/`. Лог: `tail -n 100 /var/log/alter-backup.log`. Восстановление проверяется на отдельной тестовой базе через `pg_restore`, а не поверх рабочей базы.

## Правила эксплуатации

1. `.env` не коммитить.
2. Перед изменениями схемы делать проверенный `backup-db.sh` или `backup-db-to-s3.sh`.
3. После изменений запускать pytest и `docker compose up -d --build`.
4. Ежедневно создавать backup базы на VPS и отправлять его в Object Storage.
5. После сбоя сначала смотреть `docker compose logs -f bot`.
6. Новые функции добавлять только после проверки реальным диалогом.
7. Для проверки поиска использовать запросы «Расскажи мне про Курта Кобейна» или «Какая сегодня погода в Москве?» и убедиться, что ответ содержит блок источников.
8. Для YouTube отдельно проверять ссылочный запрос и аудиозапрос: «Найди клип Nirvana» и «Включи песню Nirvana».
9. После настройки backup проверить ручной запуск и восстановление на отдельной тестовой базе.

10. Для обычных содержательных сообщений используется search-first через Tavily; погода идёт через `wttr.in`, YouTube — через YouTube API.
11. Фото и видео обрабатываются vision-веткой с последними сообщениями сессии и памятью, чтобы media-ответ продолжал один диалог.
12. Если Redis становится read-only или временно недоступен, `GuardMiddleware` пропускает billing/spam-проверку и не блокирует сообщения; Redis остаётся вспомогательной инфраструктурой.

13. Перед изменениями проверять `py -m pytest -q`, `py -m compileall -q .` и offline smoke-сценарии; Docker нужен только для интеграционного запуска на сервере.
14. При анализе качества смотреть не только на ответ AI, но и на выбор модели, tool calls, память и длительность через `metric_count`/`metric` в логах.
15. Перед релизом запускать `py -m pytest -q tests/test_smart_eval.py`; это минимальный контракт интеллектуального поведения ALTER.
16. Не добавлять новые списки trigger-фраз для поиска. Расширять нужно описания инструментов, planner и eval-сценарии.

## Ближайшие улучшения логики

- добавить сценарные eval-тесты на память, исправления фактов, `open_loops`, отказ от лишнего поиска и корректный выбор reasoning-модели;
- ввести явный confidence/источник для извлечённых фактов, чтобы сомнительные выводы не попадали в долговременную память;
- сделать отдельный планировщик задач: сначала понять цель, затем собрать контекст, выбрать инструменты, выполнить шаги и проверить результат;
- добавить дедупликацию и устаревание vector memory, чтобы старые похожие сообщения не засоряли prompt;
- после накопления реальных логов подключить Prometheus/Loki для графиков latency, fallback rate и ошибок по инструментам.

## Состояние после большой итерации

Сделано:

1. Надёжный AI fallback и выбор быстрой/reasoning-модели по смыслу пользовательского запроса.
2. Planner/executor с allow-list инструментов, структурированными статусами результата и лимитом до 6 раундов по умолчанию.
3. Семантический поиск для текста, медиа и audio action без trigger-фраз в handler-логике.
4. Долговременная JSONB-память, vector memory, merge без потери фактов, `open_loops` и исправление пользовательских данных.
5. Безопасное поведение при сбоях AI, поиска, embeddings, Whisper, TTS, Redis и PostgreSQL.
6. Quality gate финального ответа и grep-friendly метрики.
7. Offline smoke/eval-контур: `120 passed`, компиляция проекта проходит без Docker.

Главный оставшийся шаг — не добавлять новые кнопки, а научить planner проверять фактическую корректность сложных ответов по нескольким источникам и собирать накопленные eval-результаты в долгосрочный quality dashboard.
